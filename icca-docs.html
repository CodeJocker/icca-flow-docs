1. Purpose & High-Level Architecture

Two cooperating backend services: auth/ (central identity & session authority) and app1/ (client application delegating authentication). Implements lightweight CAS/SSO login flow with signed redirects, refresh rotation, and internal service tokens.

Auth Service

  • User & session registry (refresh tokens hashed)
  • OAuth2 (Google), email/password, HMAC-signed redirects
  • Client app allowlist, audit logs, roles/permissions
  • Service JWT & internal APIs

App Service

  • Initiates login/register redirects with signed state
  • Stores state cookie (CSRF protection)
  • Validates callback token & state match
  • Delegates authentication 100% to auth service
5-step core loop: App request → signed redirect → auth validation → user auth + session → redirect back with token → app state verification.

3. Trust Boundaries & Signed Auth Request

HMAC signature validation: required fields client_id, service, state, timestamp, sig, action. Payload format:

client_id:service:state:timestamp

Auth service recomputes HMAC with TOKEN_HMAC_SECRET, checks timestamp freshness, client existence, and that the service URL belongs to allowed_redirect_urls. Prevents token redirection to unapproved destinations.

Redirect validation: Even with valid signature, the requested redirect_type and service origin must be allowed by client registration.

4. End-to-End Critical Flows

A. App initiates login/register

GET /auth/redirect → generates random state, timestamp, builds HMAC → stores signed stateCookie → redirects to auth with action, client_id, service, state, sig.

B. Auth validates & shows UI

Auth verifies signature, redirect allowlist, stores validated context in signed 'cas_params' cookie. If existing session (refresh token valid) → instant redirect back to app, else forward to login/register page.

C. Email/Password login

POST /login → authenticate credentials → createSession (access + refresh token, hashed refresh stored in DB with family) → set cookies & redirect to app callback with token + state.

D. Google OAuth

Exchange Google code → find or link user by googleId/email → create/update user profile → issue session tokens → same redirect flow as normal login.

E. App callback

GET /auth/callback → reads state & access_token → compares with signed stateCookie → if match, token accepted for application session.

Note: app1 expects access_token in callback, while auth redirect builds token – naming mismatch documented.

5. Session & Token Lifecycle

🔐 Creation: generate JWT pair → hash refresh token → store RefreshToken doc with family, expiry, IP, userAgent → return raw tokens.
🔄 Rotation (/refresh): validate old token → revoke old entry (revokedAt/replacedBy) → issue new family member → new DB row & cookies.
🚪 Logout: delete refresh token document → clear cookie. No server-side orphan.

Session hydration: sessionService.getSession reads refreshToken cookie, verifies JWT, then looks up hashed token in RefreshToken collection (with legacy user.token fallback). Fresh tokens issued on reuse.

6. Registration & Password Reset

  • Registration → POST /register, duplicate email blocked, password hashed, email verification OTP generated → user created with status: pending_verification AND session created immediately (tokens returned).
  • Forgot password → generate raw reset token, store SHA256 hash + expiry → send Brevo email with reset link (targeting auth reset action).
  • Reset password → POST /reset-password with raw token + new password → hash token, match stored token hash → update password, clear reset fields, but current controller returns success without setting new session cookies.

7. Service-to-Service & Internal APIs

POST /api/v1/auth/token → signed client validation, scopes_allowed check → issues short-lived service JWT (type: "service") for backend communication. Internal routes (e.g., PATCH /service/users/:id/role, GET /internal/users/:id) are protected by verifyServiceToken middleware which requires type: service and the "roles" scope for all protected calls. Returns effective permissions, profile updates, audit logs.

Service token payload includes client_id, scopes, exp. Used for trusted backend → backend authorization.

8. Admin, Roles & Permissions

Permissions computed as role base permissions ∪ AccessControl direct permissions. super_admin gets all keys. Default roles: member, admin, super_admin with modules: mentors, mentees, resources, reports, users, notifications.

Admin endpoints protected by verifyToken + requireSuperAdmin. Actions: create/update/disable admin, assign/revoke permissions, list audit logs. Each admin action writes AuditLog entry.

Bootstrapping: authorizationService.ensureSystemRoles.

9. Cookies, Redirects, State

🔐 Auth cookies: refreshToken (httpOnly), user (non-httpOnly), cas_params (signed validated context)
📱 App cookie: stateCookie (signed CSRF protection)

Query parameters between services: action, client_id, service, state, timestamp, sig. Callback returns token + state from auth to app (naming mismatch with access_token).

11. Important Implementation Notes

  • Refresh sessions stored in RefreshToken collection, but hydration still contains legacy user.token lookup.
  • Registration creates immediate session even though status may be pending_verification.
  • Reset password creates tokens inside service layer but controller does NOT set cookies or return tokens.
  • sessionService.autoLoginRedirect uses token URL param, while app1 reads access_token → naming mismatch risk.
  • verifyServiceToken requires roles scope for both /service and /internal routes, locking internal profile reads behind that scope.
  • Google OAuth flow updates missing local fields (fullName, gender, googleToken) and upserts verified users.
Core mental model: Auth owns identity & sessions, App relies on signed redirects & state verification.HMAC + refresh token family + audit trail
