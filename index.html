🚀 User Onboarding Journey: App → Auth → Onboarding Flow

This section details the complete user experience starting from accessing the application, authentication delegation, and the post-login onboarding orchestration — including UI state changes, background token exchange, and onboarding completion screens.

1. Access App

User visits app.example.com

2. Member Login

Clicks "Member Login" → triggers signed redirect

3. Auth Service

Validates HMAC, checks client, shows login UI

4. Authentication

Email/password or Google → session & tokens

5. Redirect back

App callback → state verification → token acceptance

Background Technical Flow (Auth + App service)

① User clicks "Member Login" → App generates random state → builds HMAC over client_id:service:state:timestamp → stores signed stateCookie → redirects browser to /api/v1/auth/redirect with action=login.

② Auth service validation → verifies signature, timestamp freshness, client allowlist → persists validated context in signed cas_params cookie.

③ User authenticates (email/password or Google) → auth creates access token + refresh token (hashed & stored in MongoDB with family).

④ Auth sets cookies (refreshToken, user) → redirects back to app callback (/auth/callback?token=&state=).

⑤ App service compares state from query with signed cookie → if match, app accepts token and changes UI state.

UI Mutation: The "Member Login" button is programmatically replaced by a "Get Started" button after token validation & user session detection.

Step A: "Get Started" click

After successful authentication, the dashboard detects onboarding status (via flag / profile completeness). If onboarding not completed, user is routed to the onboarding screen (multi-step profile, preferences, etc.).

Step B: Onboarding in progress

User provides required information (nationality, basedIn, skills, etc.). Data is stored in Auth service User model fields + potentially app-specific collection. Each step updates the user profile incrementally.

Step C: Onboarding complete

When all steps finished, the system displays an Onboarding Success Screen → marks user onboardingCompleted=true (custom flag) → user can access full dashboard. The "Get Started" button is replaced by "Go to Dashboard".

1. Purpose & High-Level Architecture

Two cooperating backend services: auth/ (central identity & session authority) and app1/ (client application delegating authentication). Implements lightweight CAS/SSO login flow with signed redirects, refresh rotation, and internal service tokens.

Auth Service

  • User & session registry (refresh tokens hashed)
  • OAuth2 (Google), email/password, HMAC-signed redirects
  • Client app allowlist, audit logs, roles/permissions
  • Service JWT & internal APIs

App Service

  • Initiates login/register redirects with signed state
  • Stores state cookie (CSRF protection)
  • Validates callback token & state match
  • Delegates authentication 100% to auth service
5-step core loop: App request → signed redirect → auth validation → user auth + session → redirect back with token → app state verification.

3. Trust Boundaries & Signed Auth Request

HMAC signature validation: required fields client_id, service, state, timestamp, sig, action. Payload format:

client_id:service:state:timestamp

Auth service recomputes HMAC with TOKEN_HMAC_SECRET, checks timestamp freshness, client existence, and that the service URL belongs to allowed_redirect_urls. Prevents token redirection to unapproved destinations.

Redirect validation: Even with valid signature, the requested redirect_type and service origin must be allowed by client registration.

4. End-to-End Critical Flows

A. App initiates login/register

GET /auth/redirect → generates random state, timestamp, builds HMAC → stores signed stateCookie → redirects to auth with action, client_id, service, state, sig.

B. Auth validates & shows UI

Auth verifies signature, redirect allowlist, stores validated context in signed 'cas_params' cookie. If existing session (refresh token valid) → instant redirect back to app, else forward to login/register page.

C. Email/Password login

POST /login → authenticate credentials → createSession (access + refresh token, hashed refresh stored in DB) → set cookies & redirect to app callback with token + state.

D. Google OAuth

Exchange Google code → find or link user by googleId/email → create/update user profile → issue session tokens → redirect flow.

E. App callback

GET /auth/callback → reads state & access_token → compares with signed stateCookie → if match, token accepted.

Note: naming mismatch between token (auth redirect) and access_token (app expectation).

5. Session & Token Lifecycle

🔐 Creation: generate JWT pair → hash refresh token → store RefreshToken doc with family, expiry, IP.
🔄 Rotation: validate old token → revoke old entry → issue new family member → new DB row & cookies.
🚪 Logout: delete refresh token document → clear cookie.

Session hydration: sessionService.getSession reads refreshToken cookie, verifies JWT, then looks up hashed token in RefreshToken collection (with legacy user.token fallback).

6. Registration & Password Reset

  • Registration → POST /register, duplicate email blocked, password hashed, email verification OTP generated → user created with status: pending_verification AND session created immediately.
  • Forgot password → generate raw reset token, store SHA256 hash + expiry → send Brevo email with reset link.
  • Reset password → POST /reset-password with raw token → hash token → update password, clear reset fields, controller returns success without setting new session cookies.

7. Service-to-Service & Internal APIs

POST /api/v1/auth/token → signed client validation, scopes_allowed check → issues short-lived service JWT (type: "service") for backend communication. Internal routes protected by verifyServiceToken requiring "roles" scope. Returns effective permissions, profile updates, audit logs.

Service token payload includes client_id, scopes, exp. Used for trusted backend → backend authorization.

8. Admin, Roles & Permissions

Permissions computed as role base permissions ∪ AccessControl direct permissions. super_admin gets all keys. Default roles: member, admin, super_admin with modules: mentors, mentees, resources, reports, users, notifications.

Admin endpoints protected by verifyToken + requireSuperAdmin. Actions: create/update/disable admin, assign/revoke permissions, list audit logs. Each admin action writes AuditLog entry.

Bootstrapping: authorizationService.ensureSystemRoles.

9. Cookies, Redirects, State

🔐 Auth cookies: refreshToken (httpOnly), user (non-httpOnly), cas_params (signed validated context)
📱 App cookie: stateCookie (signed CSRF protection)

Query parameters between services: action, client_id, service, state, timestamp, sig. Callback returns token + state from auth to app.

11. Important Implementation Notes

  • Refresh sessions stored in RefreshToken collection, but hydration still contains legacy user.token lookup.
  • Registration creates immediate session even though status may be pending_verification.
  • Reset password creates tokens inside service layer but controller does NOT set cookies or return tokens.
  • sessionService.autoLoginRedirect uses token URL param, while app1 reads access_token → naming mismatch risk.
  • verifyServiceToken requires roles scope for both /service and /internal routes.
  • Google OAuth flow updates missing local fields (fullName, gender, googleToken) and upserts verified users.
